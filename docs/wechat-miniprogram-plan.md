# 微信小程序（只读浏览端）方案

起草：2026-11-10 · 状态：2026-11-10 方案冻结，未开始编码
范围：微信小程序首版，只读浏览。不含族人录入、不含后台管理。本文只做选型与清单，确定后再动手写代码。

前置口径：个人主体，example.com 已 ICP 备案。

---

## 一、结论先说

1. **用原生小程序重写浏览端**，不用 Taro / uni-app，首版也不做 `web-view` 套壳。理由见第四节。
2. **首版不接微信登录**，只做匿名浏览 + 族谱访问口令。小程序里没有用户账号，也就不收集个人信息，审核面最小。
3. **后端要加一条 Token 通道**（Bearer），因为小程序的 `wx.request` 不走浏览器 Cookie，现有 `fg_session` / `fg_t_<slug>` 那套机制在小程序里用不上。
4. **访问口令只做族谱级**（2026-11-10 定）：哪部谱设了口令就要输，没设的直接看；不设「打开小程序先输密码」的总门禁。机制沿用现有 `POST /api/t/:slug/access`，不新造一套。
5. **最大的工作量在世系图和谱页**，不在页面框架。两者都已降级到可控范围：世系图走缩进树，谱页只做阅读模式。
6. **在世族人隐去敏感项**：显示姓名、世次、房支，隐藏生年、生平、葬地、头像，由服务端按 `view=mp` 裁剪（见 5.3、第九节）。这是过审的关键一条，已定。
7. **不做族人头像**，头像位改成微信式圆角矩形，块内显示完整姓名（见 6.6）。

## 三、首版功能范围

按你选定的「只读浏览」，首版就这五块：

| 模块 | 内容 | 对应现有页面 |
|---|---|---|
| 族谱总目 | 列出可公开访问的族谱，点进去 | `src/pages/Portal.tsx` |
| 家族首页 | 名号、堂号、郡望、源流、家训、统计（人数 / 世次 / 房支） | `src/pages/Home.tsx` |
| 族人名录 | 按世次、房支筛选，搜索，点开看详情 | 由世系图数据派生 |
| 世系图 | 树状层级浏览，点节点展开 / 定位 | `src/pages/Genealogy.tsx` |
| 谱页 | 按世代分卷的阅读模式 | `src/pages/PrintPage.tsx` |

明确不做：信息反馈提交、家族文献长文页（第二期再加）、任何编辑入口、微信登录、分享带参统计。

家族文献（`/t/:slug/literature`）是长文本页，做起来便宜，但既然你没点它，先放二期。

## 四、技术选型

### 4.1 为什么不套壳（web-view）

`web-view` 嵌 example.com 的响应式页面，三五天能出可提交版本，但代价是：

- 页面里所有交互都由网页自己处理，小程序无法自定义导航、无法页面级分享卡片、无法用微信能力。
- 个人主体使用 `web-view` 需要配置「业务域名」并上传校验文件，还要接受审核方对「整站套壳」的判定，被拒概率不低。
- 现有前端是 React SPA，首屏加载在移动网络下并不轻，套壳等于把网页的弱点原样搬进小程序。

结论：套壳适合「先占位、不做产品」，你既然要做只读浏览端，走原生更值。

### 4.2 为什么不用 Taro / uni-app

现有前端 115 个 `.tsx`、shadcn/ui 组件、Tailwind 样式、`@xyflow/react` 世系图。Taro 对这套组合的兼容度很低，Tailwind 在 Taro 里需要额外编译链，React Flow 完全不可用。实际复用率接近 0，多一层框架只增加构建和排错成本。

### 4.3 选定方案

- 原生小程序（微信开发者工具）+ TypeScript，不用 UI 框架，自己按现有视觉语言写 WXSS。
- 视觉沿用 `project_visual_language` 那套：宋体标题、黑体正文、现有四色。小程序端不重新设计，避免两套观感。
- 图标用 SVG 转 base64 或 iconfont，不用图片图标。

## 五、后端要改什么

现有的只读接口已经够用，缺口只有两处：鉴权通道、数据量。

### 5.1 Token 通道（必做）

现状：`requireTenantAccess`（`server/app.ts:1017-1051`）只从 Cookie 读 `fg_t_<slug>`。小程序没有 Cookie 自动管理。

最小改动方案：

1. `POST /api/t/:slug/access` 校验口令通过后，除 `Set-Cookie` 外**同时在 JSON body 返回 token**（复用 `createTenantToken` 生成的同一串，`server/auth.ts:181`）。
2. `requireTenantAccess` 增加回退：Cookie 缺失时读 `Authorization: Bearer <token>`。
3. token 有效期：网页端 1 天不变，小程序端 **7 天**（2026-11-10 定）。实现方式为 `createTenantToken` 增加可选 `ttlMs` 参数（默认仍取 `TENANT_TTL_MS`，`server/auth.ts:165`），`access` 请求体带 `channel: "mp"` 时按 7 天签发并同时返回 token。到期后小程序回解锁页重输，不做静默续期。

不需要改：CORS（`wx.request` 不受浏览器同源策略约束）、同源校验（`server/app.ts:768-802` 对缺失 `Origin` / `Sec-Fetch-Site` 的请求放行，小程序请求正好缺这两个头）。

需要确认：这条放行口子等于「任何非浏览器客户端都能直接调写接口」。首版只读不涉及，但小程序端上线后，如果你以后加录入功能，得给写接口补一层来源校验。

### 5.2 匿名可读的接口（直接可用）

| 接口 | 位置 | 用途 |
|---|---|---|
| `GET /api/public/families` | `server/app.ts:1069` | 总目列表 |
| `GET /api/t/:slug/family` | `server/app.ts:1291` | 家族首页信息，不校验口令 |
| `GET /api/t/:slug/stats` | `server/app.ts:1295` | 统计，需口令 |
| `GET /api/t/:slug/members` | `server/app.ts:1303` | 世系图 / 名录 / 谱页唯一数据源，需口令 |
| `GET /avatars/:key` | `server/app.ts:2267` | 头像，**小程序端不使用**（见 5.3） |

### 5.3 两处已知冲突

**头像冲突已消解（2026-11-10 定：小程序端不做头像）。** 原本的难点是 `<image>` 组件无法附加 `Authorization`，非公开谱的头像接口（`server/app.ts:2272-2296`）会拒绝，只能走「拉 arraybuffer 转临时文件」这种绕法。既然定了不显示头像，这条不用处理，`avatar_key` 也已在 `view=mp` 里置空。

附带的收益：`wx.request` 拉二进制 + 文件系统写入在低版本基础库上有兼容差异，不开这个口子就省掉一类真机问题。

**members 接口全量返回（2026-11-10 定，不分片）。** 真实规模 100–500 人，`/api/t/:slug/members`（`server/app.ts:1303`）一次返回全族可行，500 人的 JSON 约几百 KB，`setData` 能承受。分片接口不做，省掉一整套懒加载逻辑。

但需要给这个接口加一个裁剪参数，同时解决两件事：

- `GET /api/t/:slug/members?view=mp`：服务端对 `is_alive = 1` 的成员把 `birth_year`、`bio`、`burial_place`、`avatar_key` 置空（字段定义见 `server/schema.sql:56-63`），再返回。
- 不加参数时行为不变，网页端照旧拿全量。

注意：裁剪必须在**服务端**做。小程序端拿到全量再隐藏，抓包就能看见，等于没做。这也意味着小程序的裁剪只降低小程序渠道的暴露面，网页版仍是全量展示——若你希望网页版也藏，那是另一个改动，需要单独决定。

### 5.4 访问口令流程（2026-11-10 定）

口径：**只做族谱级口令，不设小程序总门禁。** 沿用现有 `POST /api/t/:slug/access`（`server/app.ts:1398`），口令哈希与限流复用 `server/rate-limit.ts`，不新造机制。

小程序端流程：

1. 进某部族谱先取 `/api/t/:slug/family`（公开接口，不校验口令），读 `hasPassword` 判断是否需要解锁。
2. 需要口令时进 `pages/unlock`，页面上必须显示族谱名，避免用户不知道在给哪部谱输密码。
3. 提交后调 `access` 接口；服务端除 `Set-Cookie` 外，同时在响应体返回 token。
4. token 存 `wx.setStorageSync`，按族谱 slug 分别存，后续请求带 `Authorization: Bearer <token>`。
5. 任一族谱接口返回 401 时清掉该谱的本地 token 并回 `pages/unlock`；返回 429 时按服务端文案显示「请 N 分钟后再试」，不做本地计时。
6. 冷启动读出 token 直接试请求，失败再回解锁页。

已知边界：

- **私密谱（`private`）在小程序里不可见。** 该档只对管理员登录可读，小程序首版没有管理员会话，按「不存在」处理，与网页端对非管理员的规则一致。
- **限流按「族谱 + 来源 IP」计。** IP 取 nginx 覆盖的 `X-Real-IP`（`server/app.ts:123`），手机流量在运营商 NAT 后共用出口，同一出口多人同时输错会一起被锁 10 分钟。用户量上来后若出现误锁投诉，再考虑改成「族谱 + IP + 小程序端本地退避」双层。
- **口令不得写进小程序包。** 口令只存在服务端哈希里，小程序端除输入框外不保留明文。

解锁页文案（固定展示，借鉴同类已上线小程序的过审写法）：

> 本谱资料仅限家族成员查看。输入的访问口令仅用于校验您是否有权查看，本小程序不收集、不留存任何个人信息。

这句话同时应对审核和隐私保护指引要求：微信平台规定小程序不得强制收集个人信息，本模式不收集任何信息；若日后新增「申请审批」模式会收集姓名，才需在后台配置《用户隐私保护指引》并申报类型。

二期可选：申请—审批模式

若日后需要「可撤销访问」或「实名留痕」，可在口令之上叠加申请审批：用户在小程序填姓名 + 备注 → 管理员审批 → 按 openid 放行。**前提是小程序端先接入微信登录（openid），首版未接。**

入口落点（已定口径）：审批界面直接加在现有网页端 `/admin`，**不复用小程序端做管理页**。管理员本就在网页端登录维护族谱，复用现有管理员会话即可，不必在小程序里再造一套带登录的管理界面，也避免首版就引入「普通族人 / 管理员」双身份。

连带改动：

- 服务端放行模型从「口令」扩为「口令 + openid 白名单」：审批通过写的是「该 openid 可看某部谱」，不是下发新口令。
- 申请表（姓名、备注、openid、状态、时间戳）+ 提交接口 + 查询状态接口 + 审批接口。
- 网页端 `/admin` 一个列表页（姓名、备注、提交时间、通过/拒绝），复用管理员会话。
- 通知闭环：审批通过后用订阅消息通知用户回到小程序；用户需提前授权订阅，否则只能自行刷新状态。
- 管理员靠「姓名 + 备注」判断申请人是否为本族人（如备注「我是 XX 的孙子」），openid 本身不可读。

工作量约 3–5 人日，主要在服务端放行模型与 `/admin` 审批页，不在小程序端。首版不做，理由：口令已能满足族人查看；审批链条长、管理员维护成本高；且接入 openid 会打破「首版不接微信登录」的边界。

## 六、小程序页面结构

已拍板（2026-11-10）：**底部 tabBar 三项**；无参数冷启动时**单谱直进、多谱先总目**；世系图**默认展开到第 5 世**。

### 6.1 页面清单

```
tab 页（底部 tabBar，png 图标）
  pages/family/index    族谱     内容随可读谱数量切换，见 6.2
  pages/tree/index      世系     缩进树，默认展开到第 5 世
  pages/members/index   名录     按世次分组，搜索 + 筛

普通页（页面栈，push 进入）
  pages/unlock/index    口令解锁
  pages/member/index    族人详情（从名录/世系进入）
  pages/print/index     谱页阅读模式
  pages/about/index     关于本系统 / 隐私与条款
```

谱页不是 tab 页，入口放在「族谱」tab 的首页里，与「查看世系图」「查看名录」并列。四个 tab 太挤，且谱页属于低频阅读，不该常驻底部。

图标：3 项 × 2 态 = 6 个 png，尺寸 81×81，单张 ≤ 40KB。从 lucide 取 `home` / `network` / `users` 转 png 即可，不用另画。

### 6.2 tab[0]「族谱」的行为分支

tabBar 页不能用 `switchTab` 带参数，所以「哪部谱」不能放在 URL 里，只能放全局状态。这决定 tab[0] 必须按状态渲染：

| 状态 | tab[0] 显示 | 顶部 |
|---|---|---|
| 可读族谱 = 1 部 | 直接是该谱首页 | 标题即谱名，无切换器 |
| 可读族谱 > 1 部且未选谱 | 族谱总目列表 | 标题「族谱总目」 |
| 已选中某部谱 | 该谱首页 | 谱名 + ⌄ 切换器 + 「‹ 全部族谱」 |

冷启动规则（`app.onLaunch` 里解析）：

1. 带 `?slug=` 参数（分享卡片、二维码）→ 直接置 `currentSlug`，落在参数指定的页面。
2. 无参数 → 调 `/api/public/families` 取可读谱数量：1 部则置 `currentSlug` 直进；多部则清空 `currentSlug`，tab[0] 显示总目。

### 6.3 切谱与状态同步（必须统一，否则会看到错谱）

- `wx.switchTab` 不支持 query，slug 一律存 `app.globalData.currentSlug`。
- 三个 tab 页各自记下「已加载的 slug」，在 `onShow` 里与 `globalData.currentSlug` 比对，不一致就重载数据。
- 切谱只从 tab[0] 的 ⌄ 或总目列表触发；触发时先把三个 tab 的本地状态清空（members 缓存、展开层级、筛选条件），再 `switchTab`，避免残留上一部谱的展开状态。
- 口令 token 按 slug 分键存，切谱不互相影响；切到需要口令且未解锁的谱，tab[0] 显示解锁入口，世系与名录 tab 显示「需要访问口令」占位并提供跳转。

### 6.4 深链与解锁的配合

分享卡片路径形如 `pages/tree/index?slug=huang&focus=123`。带 `slug` 进来时，无论目标页是哪个：

1. 命中 401 → 进 `pages/unlock`，**记下目标页与参数**；
2. 解锁成功后 `redirectTo` 回原目标页，不能落回 tab[0]。

### 6.5 状态管理

一个轻量全局存储（`app.globalData` + 订阅）保存「currentSlug、token 表、family 信息、members 缓存、三 tab 各自视图状态」，等价于网页端 `src/lib/tenant-context.tsx`。不引第三方状态库，小程序这点体量用不上。

### 6.6 头像位：矩形姓名块（不做头像，2026-11-10 定）

小程序端不做族人头像。原头像位置改成一个**圆角矩形姓名块**，参照微信头像的矩形制式，**不用圆形**。块内显示**完整姓名**，本族人与外姓配偶同一套规则，不去姓、不改写成「X氏」。

字号按姓名长度分档，避免长名挤成一团：

| 姓名长度 | 排列 | 小号 88rpx | 大号 176rpx |
|---|---|---|---|
| 1 字 | 居中 | 40rpx | 80rpx |
| 2 字 | 一行两字，字距 2rpx | 30rpx | 60rpx |
| 3 字 | 两行，上 2 下 1 居中 | 26rpx | 52rpx |
| 4 字及以上 | 两行，每行至多 2 字 | 22rpx | 44rpx |

- 圆角 12rpx（小号）/ 20rpx（大号），保持矩形观感，不裁圆。
- 底色按 `id % 4` 取现有四色浅色，文字用深色，保证对比度；同一人颜色固定。
- 文字居中，不换行溢出、不加省略号。字号已按长度预先分档，不做运行时缩放。
- 小号用于名录列表项、世系树节点；大号用于详情页顶部。

**排版约定**：块内已是完整姓名，列表项右侧不再重复写一遍姓名，只放世次、房支等元信息；详情页顶部为大号块 + 一行姓名，姓名右侧放世次。这样不会出现「块里写黄庭坚、旁边又写黄庭坚」的重复。

搜索按完整 `name` 匹配，输全名或其中任一字都能命中。

## 七、世系图与谱页怎么在小程序里做

这是两个真正花钱的地方。

### 7.1 世系图

网页端是 `@xyflow/react`（DOM 节点 + SVG 连线 + 自研布局 `src/components/tree/layout.ts`），小程序没有 DOM，整块不可复用。三条路：

| 方案 | 做法 | 效果 | 工作量 |
|---|---|---|---|
| A 缩进树 | 纯 WXML 层级缩进，点击展开 / 收起，竖向滚动 | 朴素但清晰，千人也不卡 | 3–4 人日 |
| B canvas 自绘 | 用 `canvas 2d` 画节点与连线，手势缩放拖拽，布局算法从 `layout.ts` 移植 | 接近网页观感 | 8–12 人日 |
| C 跳浏览器 | 图页给「在浏览器中查看完整世系图」按钮 | 体验断裂 | 0.5 人日 |

**已定：A 缩进树（2026-11-10）。** 理由：真实族谱 100–500 人，canvas 的优势体现不出来；核心用户是族中长辈，缩进树比可拖拽的图更好认；3–4 人日就能做完，二期若确有需要再上 B。

交互（已定）：默认展开到第 5 世，节点右侧带「N」人数角标，逐层点开收起；顶部房支 chips 切换；长按节点定位。

实现要点：缩进层级用 WXSS 的 `padding-left` 逐级累加，不用嵌套 `view` 太深（小程序节点数多了会卡渲染）。折叠状态只存「已展开的 id 集合」，默认集合 = 第 1–5 世全部 id，切谱时清空重算。

二期可选：canvas 自绘树状图（B 方案）

若族人反馈缩进树不够直观、想要接近网页版的可拖拽全景图，可上 B：用 `canvas 2d` 画节点与连线，支持手势缩放、平移，布局算法从网页端的 `src/components/tree/layout.ts` 移植。工作量约 8–12 人日，主要在绘制与手势、低端机掉帧优化。

注意：B 方案的「图」和首版的「树」是两套渲染，不是叠加。上 B 时首版 A 的交互要整体替换：

- 「默认展开到第 5 世」不再成立，改为 **默认 fitView 到始祖 + 自动缩放**到合适层级；
- 「点击展开/收起节点」改为 **缩放手势 + 双击聚焦某节点**；
- 节点左侧的矩形姓名块（6.6）在 canvas 里要手绘，字号分档逻辑照用；
- 「N」人数角标、房支 chips 切分、长按定位仍可保留，但实现从 WXML 事件变成 canvas 命中检测。

是否真上 B，等首版上线后看族人实际查看习惯再定，不预先投入。

### 7.2 谱页

网页端六档版式（`src/pages/PrintPage.tsx:44-51`）依赖 `@media print`、`@page`、分页断点（`src/styles/print.css`），小程序里没有打印概念，CSS 分页模型也不存在，重写六档等于重做一个产品。

**已定：只做阅读模式（2026-11-10）。** 按世代分卷纵向滚动，卷与卷之间插入卷首标题（第 N 卷 / 第 N–M 世），字体用宋体，保留网页谱页的视觉结构。数据复用 `/members`，样式只写一套。

卷的划分：500 人以内按「每 3 世一卷」切，人多的谱按「每 2 世一卷」，实际卷数在页面顶部做成分段可选。不做页码、不做跨卷续排。

打印需求继续走网页端，小程序里放一个**「复制网页版链接」按钮**（2026-11-10 定，选项 B）：

- 按钮调用 `wx.setClipboardData`，复制网页版谱页地址：`https://example.com/t/<slug>/print?access=<token>`。
- `access` 复用小程序已持有的 tenant token，网页端需**新增从 URL query 读取 `access` 作为已解锁凭证**（复用现有 token 校验，不新造登录态）。
- **按钮与提示文案须提醒用户「在电脑端浏览器打开」**：族谱的打印与完整六档版式以电脑端体验为佳，手机端浏览器虽能打开，但排版、打印以电脑端为准。建议按钮文字即「复制网页版链接（请在电脑浏览器打开）」。
- 隐私注意：token 会进入浏览器地址栏与历史记录。若介意，改为只复制基础地址 `https://example.com/t/<slug>/print`，用户在浏览器内自行输口令（网页端现有解锁流程即可）。
- 公开谱（无口令）复制基础地址即可，不带 token。
- 个人主体小程序不支持 `web-view`，无法内嵌网页，故采用「复制链接 + 浏览器打开」，不内嵌。

## 九、风险与审核要点

**1. 在世族人信息（已定：隐去敏感项）**

2026-11-10 定：在世者显示姓名、世次、房支，隐藏生年、生平、葬地、头像。落在 `/members?view=mp` 的服务端裁剪上（见 5.3）。

理由与遗留说明：族谱里含在世者的真实姓名与亲属关系，小程序要过平台审核，《个人信息保护法》也要求告知同意。这一档既保住「能认出人」的实用价值，又不去展示可被投诉的具体个人信息（生年、生平、照片）。

需要注意两点：一是网页版仍是全量展示，小程序只降低了小程序渠道的暴露面；二是访问口令本身不构成「告知同意」，如果族人日后提出异议，处理方式仍是从数据本身移除，而不是从某个渠道隐藏。

**2. 个人主体类目**

族谱内容偏「信息查询」，个人主体通常能过。若审核要求补充资质，备选是把小程序定位成「家族内部工具」，描述里不要出现「公开展示」「收集族人信息」这类表述。

**3. 首版无 UGC 是优势**

不接反馈提交、不接微信登录，小程序端不产生任何用户内容，审核时不需要内容审核机制说明。

**4. 姓名一律完整显示，不做省写**

头像位、列表、世系树、谱页、详情页全部显示 `name` 原值，省掉头像资产但不省字（见 6.6）。外姓配偶同样照原样显示，不强制改写为「X氏」。
